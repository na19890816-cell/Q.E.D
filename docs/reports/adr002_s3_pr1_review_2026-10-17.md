## 2. 登録後・コミット前の as-of（再現済み・未解消の制約）

書込接続 W で登録し、外側のトランザクションをコミットせずに保持した。
別の読取接続 R で DB 時計から as-of を採り、`recorded_at < as_of < W の commit` とした。
sleep やクライアント時計には依存しない。

初回再現の DB 時刻は recorded_at=`2026-10-17T03:57:00.288285+00:00`、
as_of=`2026-10-17T03:57:00.290344+00:00`。
R の読取りはコミット前 **N=0**、W のコミット後は同じ as-of でも **N=2** になり、snapshot_hash も変わった。

追加した統合テストは次を確認する。これらは既存動作の制約を記録するテストであり、解決済みを示すものではない。

- READ COMMITTED: 同じ読取トランザクション内の再問合せでも 0 → 2 に変わる。
- REPEATABLE READ: 同じ読取トランザクション内では 0 のままだが、新しいトランザクションでは 2 に変わる。
- `as_of < recorded_at` なら、コミット後もその batch は含まれない。

原因は recorded_at が INSERT 前の DB 壁時計であり、コミットの可視化時刻ではないこと。
clock_timestamp() は長いトランザクションの開始時刻を使う問題を防ぐが、登録後のコミット待ち時間は解決しない。
即時コミットやコミット直前の時刻採取でも時刻と可視化の間は残るので、履歴不変の保証にはならない。

今回は要件の検証項目 3 として再現・文書訂正を行い、既存の DSR・FROST・昇格判定・台帳読取り API は変更しない。
コミット可視性に基づく履歴固定は未実装。固定した壁時計 as-of と snapshot_hash だけでの再構成は避け、
監査再現には実際に参照した batch ID 全件と集計入力の保存が必要（現在の CLI は未実装）。
初期文書の「過去の snapshot に入らない」という無条件の記述を、上記の範囲に訂正した。
